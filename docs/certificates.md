# Certificates and keys

`dg-configurator` generates the certificates and keys an endpoint's `security` section needs, and converts certificates and keys from other formats to PEM. It is available in the web UI (**Keys & certificates…**) and on the command line (`pki` and `convert`, see [cli-reference.md](cli-reference.md)).

The Data Gateway only accepts `.pem` files, so PEM is the standard everywhere: certificates are PEM, private keys are PKCS#8 PEM (optionally encrypted), and all generated file names end in `.pem`. The editor warns (`file_not_pem`) when a `security.ca`, `security.certificate` or `security.key` file name does not end with `.pem`.

## Using the files in an endpoint

For MQTT, OPC UA and SQL endpoints:

| Field | File |
|---|---|
| `security.ca` | The CA certificate that verifies the **peer's** certificate (`ca.pem` of the PKI that issued the server certificate) |
| `security.certificate` | The gateway's own client certificate (`client.pem`, or `opcua.pem` for OPC UA) |
| `security.key` | The matching private key (`client-key.pem`), PKCS#8 PEM |
| `security.keyPassword` | The passphrase of the private key, if it is encrypted |

Add the files to the project with **Add to project files** (they are stored as `certs/<name>.pem`) or select them with the file pickers, and enter the passphrase in `keyPassword`.

## Usage profiles

Every profile marks BasicConstraints and KeyUsage as critical, adds SubjectKeyIdentifier to every certificate and AuthorityKeyIdentifier to every certificate that is not a self-signed root CA, and signs with SHA-256 (SHA-384 for P-384 keys; never SHA-1). Certificates are valid from five minutes before issue time (clock skew).

| Usage | Basic constraints | Key usage | Extended key usage | Subject alternative names | Keys | Validity default / max (days) |
|---|---|---|---|---|---|---|
| `ca` | CA, path length 0 | keyCertSign, cRLSign, digitalSignature | none | none | all | 3650 / 7300 |
| `tls-server`, `mqtt-server`, `sql-server` | not a CA | digitalSignature (+ keyEncipherment for RSA) | serverAuth | at least one DNS name or IP address | all | 825 / 3650 |
| `tls-client`, `mqtt-client`, `sql-client` | not a CA | digitalSignature (+ keyEncipherment for RSA) | clientAuth | optional | all | 825 / 3650 |
| `opcua-application` | not a CA | digitalSignature, nonRepudiation, keyEncipherment, dataEncipherment (+ keyCertSign when self-signed) | serverAuth and clientAuth | application URI first, plus at least one DNS name or IP address | RSA only | 1825 / 3650 |

"All" keys means RSA 2048, 3072, 4096 and EC P-256, P-384. The default key is **RSA 4096**: the Data Gateway hardening guideline requires keys of at least 4096 bits, so smaller RSA keys and EC keys are selectable but produce a warning. Keys are never accepted below RSA 2048.

Common-name conventions: for `mqtt-client` brokers that use the certificate identity (for example Mosquitto `use_identity_as_username`) take the common name as the user name; for `sql-client` PostgreSQL-style `clientcert=verify-full` maps the common name to the database user; server certificates should carry the host name clients connect to as a DNS name.

A leaf certificate can never be valid longer than its CA; the request is refused if it would be.

## OPC UA

An OPC UA application instance certificate (OPC UA Part 6) is generated by the `opcua-application` usage:

- `security.certificate` / `security.key` take the gateway's application certificate and its RSA PKCS#8 key (`keyPassword` for an encrypted key). The gateway's handler only reads RSA keys, so EC keys are not offered; RSA 2048 works with every security policy, and the legacy policies `Basic128Rsa15` and `Basic256` are deprecated.
- The URI subject alternative name is the application URI. It must be a valid absolute URI such as `urn:host:DataGateway:client` and equal the application URI the gateway presents. It is placed first in the subject alternative name, followed by at least one DNS name or IP address.
- The common name is the application name; an organisation (O) is recommended and a warning is shown when it is missing.
- `security.ca` takes the CA certificate that issued the **server's** certificate. For a self-signed server certificate, give that certificate file as `security.ca`.
- The OPC UA server must in turn trust the gateway's certificate: add its CA (or the certificate itself, if self-signed) to the server's trust list.
- One certificate serves both the client and the server role. `pki full --domain opcua` therefore creates two application certificates (`server.pem`, `client.pem`); each needs its own application URI.

## Generated files

| File | Content |
|---|---|
| `ca.pem`, `ca-key.pem` | CA certificate and its private key (only when a new CA is created) |
| `server.pem`, `server-key.pem` | Server certificate and key |
| `client.pem`, `client-key.pem` | Client certificate and key |
| `opcua.pem`, `opcua-key.pem` | Default names of a single OPC UA certificate created without an explicit name |

With an existing CA the CA files are not written again. A self-signed certificate is its own trust anchor: give that certificate file to the peer (there is no `ca.pem`).

Keep the CA key (`ca-key.pem`) offline once all certificates are issued, and protect every private key with a passphrase where the consumer can supply it. Unencrypted private keys produce a warning.

## Converter

The converter turns other formats into PEM. The input (at most 1 MiB) is detected automatically.

| Input | Supported | Notes |
|---|---|---|
| PEM certificates and keys | yes | Text around PEM blocks (`openssl x509 -text` output, `Bag Attributes` lines) is ignored; unknown block types are skipped with a warning |
| DER certificate (`.der`, `.cer`, `.crt`) | yes | |
| PKCS#7 bundle (`.p7b`, `.p7c`, PEM or DER) | yes | Certificates only |
| PKCS#12 / PFX (`.p12`, `.pfx`) | yes | The password is required; legacy ciphers (RC2, 3DES) are read, other unsupported ciphers produce a hint to re-export with AES-256 |
| PKCS#8, PKCS#1 (`RSA PRIVATE KEY`) and SEC1 (`EC PRIVATE KEY`) keys, PEM or DER | yes | Encrypted keys need the password |
| OpenSSH private key | yes | Unencrypted keys only; decrypt others with `ssh-keygen -p -m PEM` first |
| Public keys: PEM, DER, `RSA PUBLIC KEY`, OpenSSH text, base64 DER (`public.txt`) | yes | Written as `<name>-public.pem` |
| Java keystores (JKS/JCEKS) | no | Convert first: `keytool -importkeystore -srckeystore x.jks -destkeystore x.p12 -deststoretype PKCS12`, then convert `x.p12` |
| PuTTY `.ppk`, DSA, Ed25519, X25519 keys | no | Export an RSA or EC key in OpenSSH format |

Output: `<name>.pem` (leaf certificate, or the CA certificate if it is the only content), `<name>-key.pem` (PKCS#8, decrypted unless an output passphrase is given), `<name>-ca.pem` (the CA chain ordered leaf to root) and `<name>-public.pem`. A certificate that does not match the supplied private key is refused. Private keys are decrypted in memory only; a passphrase can be set for the converted key.
